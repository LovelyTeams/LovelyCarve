# 插件发现：手动触发，后台扫描

本文说明已经接入的手动后台发现流程。应用启动时扫描插件；运行中在“设置 → 插件”点击“检查插件目录”重新扫描。配置参考见 [plugin.toml 字段文档](PLUGIN_MANIFEST.md)，现有协议见 [LPP](PLUGIN_PROTOCOL.md)。

## 1. 触发与操作反馈

保留启动扫描，运行中由用户在插件设置页点击“检查插件目录”触发一次后台扫描。没有定时轮询、文件监听或页面打开即扫描。普通列表读取不承担扫描副作用。

桌面和生成的 CLI 命令表共用 `plugin_rescan` 命令。命令等待后台阻塞线程完成目录检查并返回报告；界面显示检查中状态，不阻塞主线程。并发检查通过同一个扫描锁串行执行，避免旧扫描覆盖新清单。退出时停止接收新检查并收尾已有扫描。

操作含义分别为：

| 操作 | 行为 |
| --- | --- |
| 检查插件目录 | 手动扫描磁盘，发布新发现的插件及诊断 |
| 读取列表 | 查询当前已发布清单和运行状态 |
| 重置插件 | 重置该插件共享实例，下次使用时重新启动；不重新发现、不替换已加载库、不终止独立任务 worker |

## 2. 扫描和发布

沿用现有根目录及优先顺序：用户数据目录、程序旁目录、额外配置目录、开发目录。插件名称不写死；按根目录直接子目录中的 `plugin.toml` 发现，支持根目录本身就是单个插件的已有规则。

一次检查按以下顺序执行：

1. 枚举候选清单，为不可读目录保留诊断，目录不存在与目录无法读取分别处理。
2. 解析清单并执行现有字段、协议校验；报告未知键，避免可选字段拼错后静默回退。
3. 解析当前平台动态库路径，确认文件存在；读取前后检查清单和库的大小、修改时间，变化中的候选报告为“文件仍在变化，请复制完成后重试”。不在扫描时加载或执行 DLL；静态检查不能证明库完整或 ABI 兼容。
4. 按已有优先顺序处理重复 ID，报告采用和被忽略的路径，不按版本号自动替换。
5. 与当前目录清单比较，生成新增、未变化、移除、更新待重启和错误记录。
6. 在短临界区发布完整清单快照和递增代际，再返回报告。扫描前后用文件元数据检查常规复制期间的变化；没有后台重试，复制完成后由用户再点击检查。扫描根目录失败时保留其原有插件，不能误当成这些插件被删除；非法或变化中的已有清单也保留原定义并附诊断。

每次检查只检查候选清单和对应动态库，不遍历、哈希整个插件目录。已有指纹继续作为详情展示，按需计算，不参与信任或可用性判断。文件大小和修改时间用于发现常规更新，不保证检测保留相同元数据的替换；替换已有插件库后仍应重启应用。

## 3. 清单与运行实例

插件目录清单采用可更新的不可变快照；运行连接、逻辑源、文件句柄、证据句柄和任务 worker 由现有运行时继续持有。不能通过替换整个 `PluginManager` 实现重新扫描，也不能因检查目录就关闭所有插件连接。

| 变化 | 发布规则 |
| --- | --- |
| 新 ID、合法清单和库文件 | 加入功能清单，首次使用时加载并握手；无需重启 |
| 未变化 | 保留定义、实例、句柄和展示指纹缓存 |
| 已有 ID 的清单或库改变 | 第一版标记“更新待重启”，保留当前定义，不在运行中热替换；扫描到的版本与运行版本分别展示 |
| 明确移除 | 不再提供新的功能入口，保留已有任务、实例及已打开文件系统直到正常结束；待执行任务报告插件不可用，不自动取消运行中任务 |
| 目录读取失败或清单暂时损坏 | 显示诊断、保留此前定义，避免一次失败破坏当前会话 |

任务 worker 和进行中的调用固定持有启动时的插件定义，避免扫描移除后仍在运行的任务因重新查找清单而失败。目录发现成功不意味着已有未知分区被自动重新打开，也不启动新插件对所有现有检材的分析任务。

## 4. 报告、事件和前端

扫描报告至少包含清单代际、扫描根目录、采用的插件目录和各项诊断；诊断含路径、可选插件 ID、状态和具体原因。检查完成后展示新增数量及需要处理的项，不将扫描失败显示成空插件列表。

`plugin-catalog-changed` 事件携带代际，每次手动检查发布后通知前端；`plugin_scan_report` 读取最近一次诊断，不扫描磁盘。插件设置页重新读取清单和报告；任务功能状态重新调用 `sched_task_functions`，使已经打开的快捷分析菜单同步变化。刷新功能清单不重置任务列表和用户当前选择；已移除功能从选择中清除，并在提交前再验证可用性。

订阅使用类型化 IPC 事件封装；面板实例释放自身订阅，任务功能单例由工作区装配清理。迟到订阅句柄立即释放，读取结果以代际校验，防止旧检查或旧案件请求覆盖新状态。

## 5. 两个仓库与打包

运行时只消费清单和动态库，不要求插件 ID 出现在主程序源码中。新增插件沿用现有 SDK/ABI 和能力类型时，独立部署不需要编译主程序。新增宿主接口或协议能力时仍需要双方升级。

构建和发布阶段从插件 workspace 下的 `plugin.toml` 生成 `src-tauri/tauri.plugins.generated.conf.json` 资源清单，桌面、便携包、CLI 包和独立插件包共用。源码插件仍须加入插件 Cargo workspace 并构建动态库；运行时扫描不会代替 Cargo workspace 注册或编译。生成资源只包含清单、当前平台动态库以及 `[library] resources` 明确声明的依赖文件，不复制源码、`target/` 等开发目录。独立生成入口是 `just plugin-bundle`，其输入为已经构建并复制到插件目录的发布资源；重打包也会重新生成清单。

主仓库继续固定插件子模块提交，SDK 和隔离宿主继续遵守版本兼容约束。打包自动发现与运行中手动扫描分别验证，不能因其中一项完成就声称另一项已实现。

## 6. 验收

- 运行中放入完整新插件，点击检查后设置页及已打开的快捷分析菜单出现对应能力；调用前不执行动态库。
- 缺库、非法清单、重复 ID、目录不可读和复制期间变化有可定位诊断，保留已有清单。
- 连续或并发检查不产生重复定义，也不会由旧报告覆盖新报告。
- 检查、移除和更新插件不终止正在执行的任务，不破坏已打开插件文件系统；移除后拒绝新任务。
- 更新已知插件显示重启生效，重置实例不被描述成更新库代码。
- 关闭面板、切换案件、退出应用时没有迟到发布、泄漏订阅或扫描后台任务。
- CLI 可显式执行相同检查命令；构建和打包加入第二个插件后不需要修改主程序中的插件名称名单。

## 7. CLI 与验证入口

CLI 中用 `plugin-rescan --json` 手动扫描，`plugin-scan-report --json` 查询报告，`plugin-list --json` 查询插件；JSONL 会话对应命令使用下划线名称，例如 `plugin_rescan`。

运行时回归使用 `just test core::extensions::plugin --lib`，前端使用 `just verify-fe`，资源生成回归使用 `just test-plugin-bundle`，CLI 使用 `just test-cli`。实际 Windows 安装包仍需按发布流程验证；macOS / Linux 包需要独立平台验证。
